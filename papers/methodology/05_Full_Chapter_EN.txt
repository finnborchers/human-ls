Methodology: Automated Collection and Structuring of Google Maps Hospital Reviews

This study investigates how publicly available Google Maps reviews can be used as a complementary data source for identifying perceived barriers, deficiencies, and experiential patterns in hospital care in Lower Saxony. The methodological foundation of this work is therefore not limited to the later analytical interpretation of review texts, but begins with the systematic construction of a reproducible review corpus. In contrast to traditional healthcare datasets, which often rely on administrative, clinical, or survey-based data structures, Google Maps reviews represent unsolicited, experience-based narratives that are written by patients, relatives, or other users after direct or indirect contact with healthcare institutions. These narratives are subjective and cannot be interpreted as verified clinical evidence. Nevertheless, they contain highly relevant signals about accessibility, communication, organization, waiting times, perceived empathy, language barriers, and other factors that are central to patient-centered healthcare research. For this reason, the data collection process was designed to transform a publicly visible but technically fragmented review environment into a structured, auditable, and machine-readable dataset.

The central methodological challenge was that Google Maps reviews are not available as a complete, static dataset through a conventional download interface. While the Google Places API provides structured place information and can return review data, the official documentation indicates that the returned review list is limited to a small subset of reviews, with a maximum of five reviews in the relevant Places resources (Google for Developers, n.d.-a; Google for Developers, n.d.-b). This limitation makes the official API unsuitable for a full-corpus analysis of hospitals with dozens, hundreds, or more than one thousand public reviews. A study concerned with systematic patterns across healthcare institutions would risk drawing conclusions from a small and relevance-sorted fragment rather than from the broader publicly visible review body. Consequently, the extraction procedure had to replicate the way review content becomes available in the Google Maps web interface: by opening the institution page, navigating to the review panel, and progressively loading additional reviews through scrolling.

The data collection pipeline was implemented in Python and consists of two main scripts, which are documented in the appendix. The first script resolves hospital names into canonical Google Maps place URLs (see Appendix 1). The second script opens these resolved URLs in a controlled Chrome browser session and captures the publicly visible review content (see Appendix 2). This separation is methodologically important because it distinguishes between two different sources of uncertainty. The first concerns whether a hospital name from the study list can be reliably matched to the correct Google Maps place. The second concerns whether the reviews attached to that resolved place can be loaded, captured, parsed, and stored with sufficient completeness and transparency. By separating URL resolution from review capture, the pipeline enables a clearer audit trail and avoids mixing place-identification errors with review-extraction errors.

The initial sampling frame was derived from a plain-text list of hospitals and clinics in Lower Saxony. Each line of this list represented one target institution and was treated as an intended sampling unit. In the first stage, the URL resolution script read this list, ignored empty lines and comments, and converted each institution name into a stable internal identifier. This identifier was not used as a scientific claim about the hospital itself, but as a technical key that allowed the pipeline to store outputs consistently across multiple runs. The script then opened Google Maps search queries for each hospital name and waited until Google Maps resolved the query into a stable place page. Because Google Maps search results may contain spelling variants, branch locations, similarly named institutions, or partially matching organizations, the script also extracted the resolved place title and compared it with the requested hospital name. This comparison used normalization rules that reduced superficial textual differences, such as capitalization, punctuation, German umlauts, and spacing. If the resolved title and the requested name were sufficiently similar, the URL was stored as a resolved place. If the title suggested a possible mismatch, the entry was marked accordingly and preserved with an error message instead of being silently accepted.

This URL lock file became a central instrument of reproducibility. Rather than searching Google Maps anew for every later review-capture run, the pipeline stored the resolved URL, resolved name, status, timestamp, and possible error message for each institution. This design allows the researcher to distinguish between successfully resolved hospitals, ambiguous cases, and failed cases. It also supports iterative correction, because mismatched institutions can be inspected manually and reprocessed without disturbing already resolved entries. In the inspected project state, the URL lock file contained 170 place entries, of which 126 were marked as resolved and 44 as mismatch. These numbers should not be interpreted as final properties of the hospital landscape, but as extraction-state indicators that document the operational coverage of the web-based data collection process at that point in time.

After URL resolution, the second stage captured reviews from the resolved Google Maps pages. This stage used the Chrome DevTools Protocol (CDP), a browser instrumentation interface that allows external tools to control Chrome and inspect browser activity programmatically (Chrome DevTools Protocol, n.d.). In practical terms, CDP enabled the script to open a real Google Maps page, interact with visible page elements, monitor network events, and evaluate the page structure while it changed dynamically. This was necessary because Google Maps is not a static website in which all reviews are present in the initial HTML document. Instead, reviews are loaded progressively while the user interacts with the page. The same behavior that a human user observes when scrolling through the review panel had to be reproduced in a controlled and documented way.

The review-capture script therefore launched Chrome with remote debugging enabled and connected to the browser through a lightweight Python implementation of the CDP communication protocol (see Appendix 2). For each institution, a temporary browser profile was created so that prior browser state, cookies, and cached information did not unintentionally affect the run. The browser language was set to German, reflecting the regional context of the study and the expected language of the interface. Once the page had loaded, the script handled the Google consent flow where necessary. This step was not a substantive part of the research question, but it was technically necessary because the consent page can prevent access to the Google Maps interface. The script attempted to select rejection or minimal-consent options where visible, using German and English label variants. If consent could not be resolved and the review panel remained inaccessible, the run was stopped and the failure reason was recorded.

Once the place page was accessible, the script identified the control that opens the complete review panel. This required a heuristic procedure because the text and structure of Google Maps interface elements can vary across institutions, languages, and interface versions. The script examined visible buttons, links, and role-based controls and assigned candidate scores based on several signals: whether the element contained review-related words, whether it displayed a review count, whether it had a JavaScript action associated with opening more reviews, and whether it behaved like a clickable button. The highest-ranked candidates were clicked sequentially until the script detected that the review panel had opened. This approach reflects a broader methodological principle of the pipeline: instead of relying on one fragile visual selector, the script combines semantic, structural, and behavioral indicators to increase robustness against minor interface changes.

The most important step of the capture process was the iterative loading of reviews. Google Maps uses lazy loading, meaning that only a small number of reviews are initially present in the page structure, while additional reviews appear as the review container is scrolled. The script therefore identified the scrollable review pane and repeatedly scrolled it toward the bottom. After each scroll action, it waited for new content to load and inspected several indicators of progress. These included the number of unique review identifiers found in the page, the height of the scrollable review container, the distance to the bottom of the panel, and review-related network activity. In addition, the script attempted to infer the declared total number of reviews from visible rating-distribution labels, when such information was available. This total served as a reference point for assessing whether the loaded review count was approaching the number displayed by Google Maps.

The stopping logic was deliberately conservative because premature stopping would reduce corpus completeness, while unlimited scrolling would make the process unstable and inefficient. The script stopped when one of several saturation conditions was met. If the declared total review count had been reached and the panel remained stable after a short waiting period, the run could stop early. If the script reached the bottom repeatedly and no further growth occurred despite additional probes, it stopped with a documented no-growth condition. If configured safety limits for scroll attempts or scrolling time were reached, the run also stopped and recorded this reason. These stopping conditions are important for methodological transparency because they make the incompleteness risk visible. A review file is therefore not only a set of extracted texts, but the result of a documented interaction process with an explicit stopping rationale.

Before storing the final review records, the script attempted to expand collapsed review texts. Long Google Maps reviews are often shortened in the interface behind a "more" control. If such controls are visible, the script clicks them before saving the final page state. It then stores the review-panel HTML as an intermediate artifact and parses review entries from this saved representation. The final structured review record includes the reviewer name displayed by Google Maps, the review text, the star rating where it can be extracted, and the relative review time as shown in the interface. In addition, the updated extraction procedure stores visible engagement and response metadata: the number of publicly displayed "like" endorsements for the review, whether an owner response is present, the displayed response time, and the text of the owner response where available. These fields were selected because they preserve the central information required for later content analysis and allow additional analysis of public engagement and institutional responsiveness, while avoiding unnecessary collection of additional profile-level information.

The extraction of these additional fields was implemented cautiously because Google Maps uses dynamically generated and potentially unstable interface class names. The parser therefore does not treat CSS class identifiers as the main evidence for likes or owner responses. Instead, it links each review to its visible thumbs-up control using the Google Maps review identifier (`data-review-id`) and the button action marker associated with toggling a thumbs-up endorsement. The displayed like count is then read from the button's accessible label or title. If the label only states "Gefällt mir", the like count is stored as zero; if the label contains a number, such as "1 „Gefällt mir“-Angabe" or "7 „Gefällt mir“-Angaben", this number is converted into an integer. Owner responses are detected through the visible interface label "Antwort vom Inhaber"; if such a label is present within the review block, the parser records the following displayed response time and response text. This design uses semantic and accessibility-oriented signals rather than relying primarily on volatile layout classes.

Deduplication was necessary because dynamic page loading can cause the same review to appear in multiple intermediate page states or retry attempts. The script primarily deduplicates records by Google Maps review identifier. If this identifier is unavailable, it falls back to a combination of normalized reviewer name and normalized review text. Where duplicate records contain slightly different information, the longer review text is preferred, and missing rating, timestamp, like-count, or owner-response fields are filled from the alternative record where possible. This procedure is designed to maximize textual completeness without inflating the number of observations. The final output for each institution is written as a JSON file, which makes the corpus directly usable for later statistical, qualitative, or AI-assisted analysis.

To increase robustness, the capture script supports repeated attempts for each institution. Later attempts can use slower scrolling, which may improve loading behavior on pages with many reviews or unstable network timing. After all attempts, the script merges and deduplicates review records across attempts and writes a final review file only if the capture was successful. Alongside the review file, the script writes a run summary and a retry summary. These metadata files contain information such as the start and end time, selected browser target, consent handling result, review-opening attempts, declared review total, final loaded review count, stopping reason, retry attempts, and output paths. This metadata is essential because it transforms the extraction process from an opaque scraping activity into an auditable data-generation procedure.

At the time of documentation, the existing review corpus contained 122 review files in the inspected artifact folder, with 31,823 extracted reviews in total. The median number of extracted reviews per institution was 200.5, with a range from 2 to 1,070 reviews. These values are not static characteristics of the research object, since Google Maps content changes over time and extraction outcomes depend on interface state, availability, and the current resolution file. They should therefore be reported together with the extraction date and understood as a snapshot of the publicly visible review environment during the collection period.

From a research-design perspective, this pipeline contributes to the overall study in three ways. First, it operationalizes a new empirical data source for healthcare access research by converting scattered public narratives into a structured corpus. Second, it preserves traceability by documenting URL resolution, capture attempts, stopping conditions, and output files. Third, it creates a methodological basis for later comparison of analytical approaches, including manual taxonomy development, statistical review-pattern analysis, topic modeling, and large-language-model-based classification. In this sense, the Python scripts are not merely technical utilities, but part of the methodological artifact of the study. They define how the raw digital environment is transformed into analyzable evidence.

However, the resulting dataset must be interpreted with caution. Google Maps reviews are self-selected public expressions and therefore do not represent the full patient population of a hospital. They may overrepresent strongly positive or strongly negative experiences, digitally active users, or users who are motivated to publish complaints or praise. The texts also reflect perceptions rather than verified facts. For the purpose of this study, this is not a weakness that invalidates the dataset, but a characteristic that defines its analytical value. The corpus is particularly suitable for studying how healthcare experiences are publicly articulated, which barriers users perceive as salient, and which recurring patterns become visible across institutions. It is less suitable for measuring objective quality of care or clinical performance.

Ethical considerations are therefore central to the use of this dataset. Although the reviews are publicly accessible, public availability alone does not remove the responsibility to minimize harm, avoid unnecessary identifiability, and treat user-generated narratives with contextual sensitivity. Internet research ethics emphasize that ethical assessment should consider the sensitivity of the data, the vulnerability of the persons involved, the expectations of the platform context, and the potential consequences of reuse (franzke et al., 2020). In this study, reviews are treated as public but sensitive experiential accounts. The analysis should therefore focus on aggregated patterns, avoid unnecessary reproduction of identifiable individual narratives, and refrain from attempts to link reviewers to external identities. This is particularly important because healthcare experiences may contain information about illness, distress, discrimination, or conflict with institutions.

Overall, the data collection method reflects the interdisciplinary character of the thesis. It combines technical browser automation, structured data engineering, and methodological safeguards in order to make a complex public web source usable for healthcare access research. By resolving hospital identities, capturing dynamically loaded review content, storing review records in JSON format, and documenting the extraction process through metadata, the pipeline establishes a transparent foundation for the subsequent analysis. It thereby supports the broader aim of this thesis: to examine whether digital traces of patient experience can contribute to a deeper understanding of barriers in the German healthcare system, particularly in areas where conventional datasets may remain incomplete, delayed, or insufficiently sensitive to lived experience.
